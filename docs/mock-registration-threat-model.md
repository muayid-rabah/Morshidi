# Mock Registration Persistence and API Threat Model

The controls below are layered. Authentication alone is never ownership, a client claim is never institutional authority, and service credentials do not remove the obligation to apply explicit owner, university, plan, and period predicates.

| Threat | Attack Path | Trust Boundary | Primary Control | Secondary Control | Failure Mode | Residual Limitation |
|---|---|---|---|---|---|---|
| Student submits another owner's ID | Add or replace `owner_user_id` in a command | `CLIENT_UNTRUSTED` to `AUTHENTICATED_IDENTITY` | API ignores/rejects owner input and derives owner from verified `auth.users.id` | Repository requires the derived owner in every key/predicate | `401`, privacy-safe `404`, or `OWNER_SCOPE_MISMATCH`; no write | A stolen valid session remains an identity-provider incident |
| Student submits another university or plan | Forge university, major, or plan identifiers | Client to `AUTHORITATIVE_ACADEMIC_STATE` | Service derives and verifies scope against the owner's authoritative profile/current plan | FK/check constraints and exact repository predicates | `PLAN_SCOPE_INVALID` or `ACADEMIC_CONTEXT_UNAVAILABLE`; no write | Correctness depends on freshness of authoritative academic sources |
| Replay of the same revision | Retry a timed-out request | Client to application service | Server fingerprint plus exact key/revision comparison | Unique revision key and atomic transaction | Same fingerprint returns the existing result without duplicate children | V1 has no general-purpose idempotency key for semantically different commands |
| Conflicting concurrent revision | Two writers use the same expected revision | Client/service to database serialization point | Required compare-and-swap on `expected_current_revision` | Exact-key lock/transaction and unique constraint | One winner; loser receives `409 REVISION_CONFLICT` | Clients must refresh before making a new choice |
| Direct Supabase insert | Browser writes intent tables through the Data API | Browser to exposed database schema | No student INSERT grant/policy | Explicit grants plus RLS; service credential remains server-only | Database rejects the write | Misconfigured future grants could weaken this control and require tests |
| Direct historical update | Browser or compromised client changes a revision | Browser to database | No UPDATE policy/grant for immutable revision resources | No application update path | Database rejects the update | Privileged operators still require controlled operational governance |
| Direct delete | Browser attempts to erase evidence | Browser to database | No DELETE policy/grant and no student hard-delete API | Withdrawal is an append-only empty revision | Database/API rejects deletion | Statutory erasure, if later required, needs a separate governed workflow |
| Institutional role escalation | Put a role/university in editable token metadata | Client claim to `AUTHORIZED_INSTITUTIONAL_MEMBERSHIP` | Server-managed membership lookup; `user_metadata` is never authorization | Exact `INSTITUTIONAL_ANALYST` check and active membership | `403 INSTITUTIONAL_ACCESS_DENIED` | Membership administration is a P6.4 prerequisite and a privileged process |
| Cross-university aggregate access | Analyst changes `university_id` query parameter | Authorized identity to tenant-scoped service | Requested university must equal an active server-authoritative membership | Repository/service enforce university predicate before aggregation | `403`; no result or existence detail | Multi-institution users need explicit membership per institution |
| Small-cohort inference | Repeatedly query narrow plan/course filters | Aggregate API to institutional user | Reuse P6.2 minimum-cohort suppression after all filters | No raw counts/rows in suppressed response; future rate controls | Suppressed result with no bypass | Differencing risk cannot be eliminated without future query auditing/rate controls |
| Raw aggregate bypass | Use `include_raw`, debug, export, or undocumented route | Institutional client to service | No raw/debug switch or raw-list endpoint exists | Response allowlist and separate future operational tooling | `422`, `404`, or ignored unsupported field; never raw data | Privileged operational access remains out of this product API's scope |
| Client-forged validation result | Submit `VALID`, reasons, or demand eligibility | Client to `P6_DOMAIN_RESULT` | Server reruns P6.1 validation from authoritative inputs | Persistence accepts only service-produced typed result | Forged fields rejected/ignored; no trusted write | A defect in server validation remains an application correctness risk |
| Client-forged fingerprint | Supply a fingerprint chosen to collide/replay | Client to persisted revision | Server canonicalizes the command and computes its own fingerprint | Persisted fingerprint compared with exact revision key | Client fingerprint rejected/ignored | Cryptographic/canonicalization implementation must be tested in P6.4/P6.5 |
| Client-forged official period | Label a period `OFFICIAL_PERIOD_REFERENCE` or alter validity | Client to target-period authority | Period identity/class/state come from provider/institution-controlled records | Service accepts only an existing authorized `target_period_id` | `PERIOD_INVALID`; no write | Declared/sandbox data must remain visibly classified by its authority |
| Stale academic state | State changes between validation and commit | Academic source to transaction boundary | Validate as close to write as possible and recheck version/state within the transaction | Later read/aggregation always revalidates without mutating history | `409 ACADEMIC_STATE_CHANGED` or stored history later excluded as stale | Cross-system sources may not offer a single distributed transaction |
| Malicious oversized course set | Submit an excessive list to exhaust CPU/DB | Client to API parser/domain service | Finite request-size and course-count limits defined by implementation configuration | Deduplicate/validate before expensive reads; future rate limiting | `422 INVALID_INTENT` or request-size rejection; no write | Exact operational limits must be benchmarked in implementation, not invented here |
| Duplicate course payload | Repeat a course in one command | Client to canonical domain command | P6.1 duplicate-course validation rejects the command | Unique child key prevents duplicate rows | `422 INVALID_INTENT`; no write | Equivalent identifiers still rely on authoritative canonicalization |
| Service credential exposure | Bundle or log the Supabase secret/service-role key in the browser | Server-only secret boundary | Secret exists only in server runtime configuration | Build/log scanning and public-bundle tests | Deployment is blocked or credential rotated; no client use accepted | Host/runtime compromise is outside RLS protection because service credentials bypass it |
| Aggregate response leakage | Add student IDs, grades, scenarios, or conversations to a response | Persistence/domain to institutional API | Typed response allowlist contains aggregate P6.2 fields only | Privacy tests and suppression pipeline | Serialization/test failure; response must not ship | New fields require renewed privacy review |
| Enumeration through not-found behavior | Probe another student's revision/resource identifiers | Student API to ownership boundary | Current endpoint is owner-derived; sensitive missing/foreign resources use the same privacy-safe `404` | No student history-by-ID endpoint in V1 | No existence signal | Timing side channels require later operational monitoring if material |

## Trust-boundary taxonomy

`CLIENT_UNTRUSTED`, `AUTHENTICATED_IDENTITY`, `AUTHORITATIVE_ACADEMIC_STATE`, `P6_DOMAIN_RESULT`, `PERSISTED_INTENT`, `AUTHORIZED_INSTITUTIONAL_MEMBERSHIP`, `VERIFIED_INSTITUTIONAL_FACT`, and `SYNTHETIC_SANDBOX_FACT` are the closed P6.3 taxonomy. Promotion between categories requires the responsible server-side adapter or service; labels supplied by clients do not change authority.
